- The church is the **Church of Notch**. Its existing resident keeps their identity and becomes a **Priest of Notch**, with seasonal dialogue about Notch and a matching entrance sign. Pew backs face the entrance, so seats face the altar.
- Generated town signs use glowing white text on both faces. The square's map kiosk and map handouts are retired; individual shop signs and guard directions remain. Maps already held by players remain valid saved items.

## Updating a town in an existing world

After installing this version, an operator uses:

```text
/jugcraft town upgrade preview
/jugcraft town upgrade apply
/jugcraft town upgrade
```

Preview/status reports how many built chunks need the current revision, how many are loaded, and the saved count of preserved edits. Apply enables a persisted upgrade request. The existing builder queue processes at most one loaded chunk per tick. Unloaded chunks resume as players visit, including after a restart. Installing the mod alone does not regenerate the town or silently replace terrain.

`TownUpgrades` compares the frozen previous blueprint with the current one. Only authored cells whose intended state changed are considered. A live cell must still match the previous expected state before replacement; already-current cells are harmless. Other blocks are preserved as conflicts. Inventories/block entities are protected; generated retired sign text is checked before removing its sign. Sign text is updated only if it still matches the previous/current authored text. Old map frames are removed only at the known kiosk anchor with the town's saved map ID, including entities loaded after the chunk upgrade.

Seasonal decoration comparisons use the town's current theme. NPC metadata refreshes preserve UUIDs and equipment. Recorded residents in unloaded chunks are retained; only confirmed destruction clears their roster binding for replacement; new spots are appended and receive a new resident when their upgraded home chunk is available. Progress, requested revision and conflict counts are saved separately from the existing town state. An interrupted upgrade can repeat safely.

### Future changes

1. Before editing the current town blueprint, freeze it as `data/jugcraft/town/revisions/<old revision>.json.gz`. Never overwrite historical snapshots.
2. Increment `TownUpgrades.CURRENT`, regenerate `town.json.gz`, and keep resident/decor spot indices stable. Append new spots; do not reuse deleted identities.
3. Test old-to-new migration, edited-block/container preservation, NPC identity, repeat application and saved progress. Test the new scene as well.
4. Deploy the tested build and run the operator command. Preserved conflicts require deliberate manual review; there is no destructive force option.

The generic comparison covers the **existing core town footprint**, including authored buildings and seasonal decoration. Terrain blending, new footprint expansions, arbitrary container conversions, removal of resident identities, and Styx's separately authored observatory district require an explicit migration for that component. They are deliberately not regenerated by this command. This first upgrade does not redesign or move the observatory. A matching block state cannot reveal who placed a block; operators should keep a normal world backup before applying any building upgrade.
