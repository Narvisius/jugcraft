# Companion shared supplies and transport

Owner-selected option 1, implemented locally with OpenAI Codex (GPT-6), 8 October 2026, on `peepo-companion`. Extends the existing companion inventory/menu, Fabric transactional storage, job adapters and server search/path budgets. No new dependencies, art, recipes or progression gates. This supersedes the single-pair setup and dedicated Porter command in [general porter](companion-general-porter.md).

## Player setup

- Select a companion with the Planner. Each new ordinary container fills the next **Supply** slot, up to four, then fills Output slots. Click an assigned container again to change just that container between Supply (blue) and Output (yellow), up to four of each. Left-click removes it. A full role refuses the change without replacing existing links. Container numbers remain stable when another is removed.
- Shift-right-click the companion and open **Supplies**. **Containers** lists the eight endpoints, with coordinates, dimension and status on hover. Mark one or more Supply containers **Tools** to allow fetching a knife for cutting boards or a hoe for garden work. **Hand: Locked** prevents automatic tool changes.
- **Job links** defaults to All Supplies / All Outputs. Selecting a number restricts that job to that container; additional numbers toggle membership. All restores shared access, including future assignments. Links follow the job when reordered. The job's existing Supply/Output Auto/On/Off controls still apply independently.
- **Porter routes** provides four independent Supply-to-Output routes without consuming the four workstation slots. Choose numbered endpoints, set an optional nine-item **Filter**, then enable the route. Changing an endpoint disables that route until explicitly re-enabled. Choose **Work** to run station jobs and routes together; the top-level Porter command has been removed.
- Inside a route Filter, **Leave** preserves a minimum source stock per item type; **Keep** limits destination stock per item type. Values cycle through 0, 16, 32, 64, 128, 256 and 512. Keep 0 is unlimited; Leave 0 reserves nothing. Empty filters accept any item. Ghost entries consume no items and match item type; transported stacks retain their real components.

## Behavior and costs

Food, recovery, schedules and settings-menu pause retain priority. Transport first tends urgent hearth batches, then fetches needed tools, then handles station outputs/ingredients in workstation order. Generic porter routes only start when no assigned productive job is ready, and rotate their starting route after each successful selection. An active delivery finishes its physical trip; a newly ready job does not teleport its cargo home.

Jobs can plan a complete recipe with ingredients split across all permitted Supply containers. The physical transfer still uses one concrete source and the existing real cargo/manifest. Full, empty, unavailable or incompatible containers are skipped during selection. Workstation outputs try other allowed Outputs; already carried workstation products can switch to another allowed Output if their destination fills. Hearth input capacity checks use all linked Outputs. An in-flight direct porter route retains its explicit destination.

Tools travel in real cargo to the assigned workstation before being equipped. The previous hand item moves into that cargo slot in the same transaction. A suitable tool already in cargo can be reused, avoiding repeated collection. Missing/broken tools can be replaced while an appropriate Tools source remains assigned and accessible. Idle cutting boards do not fetch a knife unless an allowed cutting recipe has an actual input on the board or in Supply. Locked hands retain torches/preferred tools; all eight cargo slots full with no reusable tool means waiting for space.

Transport now uses the [batch delivery](companion-batch-deliveries.md) rules: up to eight available cargo slots at normal item stack sizes, with walking cost scaled to the load. The 64-block navigation/endpoint range, normal off-wheel regeneration, and actual workstation/tool durability costs remain. No new energy currency or inventory expansion. Supplies connect existing farms/material producers to kitchens/machines; Outputs feed player storage and downstream production.

## Server behavior and persistence

Four jobs, eight container targets and four routes are fixed limits. Only assigned, loaded containers are inspected; no chunk tickets or global container/worker scans. Selection uses the existing per-server search/path budgets and staggered 80-99 tick searches. Travel validation retains its ten-tick cache; actual transfers always recheck loaded/access/permissions and use rollback-capable transactions. Candidate storage enumeration is bounded at 128 views per concrete container. Combined recipe snapshots allow up to 512 views for four sources, covering all 216 slots of four vanilla double chests. Tool searches inspect at most 32 views per Tools container; they snapshot available ingredients once per search and memoize recipe usefulness by tool type within that search. Companions with no Tools sources skip that work. Recipe preparation does not retain inventories between searches, and per-tick route membership checks avoid allocating container lists.

Stock-limit probes tally each bounded inventory once, rather than rescanning it for each stack. Source reserve and destination capacity are checked at pickup; destination targets are checked again at delivery. Inventories with more than 128 views cannot supply a trustworthy stock total, so routes with the relevant limit wait rather than bypassing it. Mutations remain sequential on the server thread, preserving contents when multiple helpers/hoppers compete.

A container has only one role per companion. Double-chest aliases are deduplicated for recipe planning, and live canonical source/destination checks prevent transferring into the same merged chest. This prevents self-loop routes within one companion. Separate companions can still be deliberately configured in opposing directions; there is no global cross-owner route graph.

Old Assignment6/Assignment7 remain Supply1/Output1. Additional numbered links use appended assignment slots. The optional SharedSupplies save section stores tool flags, hand lock, per-job masks, routes and filters. Missing settings default to All and no enabled routes. Old command value 4 migrates to Work plus an enabled Supply1-to-Output1 route; old in-flight porter cargo migrates to that route. Existing registry IDs and inventory slot IDs are retained. Clear/switch of an endpoint disables affected routes; items already carried remain real inventory and are not recreated. Update clients and server together for the extended menu synchronization.
