## Player-visible result

To view the redesign with cheats enabled, stand in an open site at least 100 blocks from an existing tower and run `/dronetest build industrial` (or add a tier from 1 to 9). This operator command creates a new industrial core if none is nearby. It refuses nearby cores using an earlier layout and explains how to choose a fresh site. The original `/dronetest build [tier]` continues the nearest core's saved design, and its feedback identifies whether that design is legacy or industrial. Both are instant-build testing aids: provide a clear footprint and enough headroom, as ordinary blocks inside the tower may be replaced.

The revised tower keeps the 215-block height and imposing silhouette. Continuous concrete blades and shear piers support solid transfer beams on bearing shoes. Clear service aprons replace the obstructed auxiliary banks around the exchanges; piping attaches to the marked outward-facing sockets. Railings stand on supported decks, and upper shoulders have closed roofs outside the required flight clearances. Exposed crown copper crossarms and unsupported girders are removed. Armored conduit remains in sheltered service runs. Ground pads move three blocks outward to make room for the wider command post; eight pads, their exit routes, elevated pickups and all hangar locations remain functional. The praised pad, pickup and sliding-door artwork is preserved. Original concrete/steel albedos supply the realistic material scale; see [the art record](drone-tower-industrial-art.md).

The command room has a 15-by-13-block interior with a centered, six-part 3x2 master console and two wall computer stations. Clear operator and cross aisles replace the desk clusters. The master console's physical controls and raised screens face its accessible operator side; equipment racks have no ventilation cabinets stacked on top. The master, wall desk monitors and main terminal show the linked tower's live fleet, active/airborne count, battery, power draw/load, pads and supply status. Two separated 3x2 wall displays show the same tower's actual fleet and power status. Console links are pinned when the tower is built and saved, with no console server ticker. Clicking any master-console part or wall desk opens the linked terminal; mode and upgrade requests carry that exact access point. The server validates the complete console, loaded block, distance and terminal link while retaining ownership checks. An unowned depot is claimed by its first console operator, matching direct terminal use. The existing terminal snapshot supplies the client readouts. The 3x3 hologram table keeps its actuator legs, service compartments and projector cradle. Its cache is independent per tower entity, including towers at identical coordinates in different worlds; first-tier site clearance does not falsely appear as placed structure.

Lighting uses sealed linear ceiling luminaires, shallow wall task lights and recessed opal floor fittings. Interior and exterior wall lights mount in adjacent air against intact walls, so the former warning-light holes are closed. Warning beacons remain only at physically supported outdoor points. The room and under-deck lights have no hanging conduit stacks. The ceiling cable trays form one continuous route with matching elbows, tees and closed terminations instead of disconnected pieces. The exported geometry checks real backing, reciprocal tray connections and brighter walking surfaces; a server light-engine regression checks every exposed full-support floor, roof and ledge in a completed tower independently of skylight.

Each regular drone now docks on its own numbered tier: T1 uses the ground pads; T2 uses the deck; T3 through T9 use their respective hangars. Creative drones can occupy any suitable spare bay. Regular drones are assigned first so creative drones cannot reserve their tier's last bay. Total physical capacity remains 133, with capacities 32 / 56 / 68 / 80 / 90 / 100 / 108 / 116 / 133. A tier can fill before the whole tower does; linking then refuses the drone without consuming its item.

The command console opens live fleet and supply displays, with a clearly labelled TOWER CONTROL button for upgrades. Readouts distinguish total drones, drones assigned to active jobs, airborne drones, battery charge and JE stored, current draw and load as a percentage of the terminal's 4096 JE/t rated input, pad/bay count and free slots. Recharge counts as an active job but not an airborne drone. Supply warnings identify a missing pickup, packager or materials. The JOBS tab scrolls long material lists with actual item icons, localized names, quantities and exact IDs in hover text. The upgrade screen shows the precise module items and held/required amounts, with scrolling support if its list grows.

## Functional MBS

Tier 1 builds a 5x5x4 Energy Exchange (64 occupied parts) and a 5x4x3 Storage Exchange (60 parts). Each has one controller block entity. An explicit saved link pins its tower, terminal, depot identity and owner. It cannot silently switch to a nearby player's depot. The designated outward-facing port feeds the existing 200,000 JE terminal buffer or existing 27-slot cargo packager. No second inventory or energy pool is introduced. Missing or wrong parts disconnect transfers, including previously obtained storage handles. The Storage Exchange opens that same inventory, with distance checked at the clicked station part; breaking its structure or changing the linked inventory closes the menu. Placement and breakage use the existing bounded MBS footprint utilities, without changing their 64-part cap. One crafted kit places a station; breaking a station returns one kit.

The power socket's sealed compression gland meets the real six-pixel cable body at the exact port center and outward block boundary. A folded cover backs the socket without a visible open seam. The outward connection corridor is clear, and nearby west bearing piers use continuous aligned concrete sections through cable height rather than stepped notches. The master console is also a real six-part MBS: one passive linked display controller serves the complete footprint, all parts share access, and assembly, rotation and breakage follow the existing MBS framework.

Station recipes consume existing steel plates, circuits, transformer casings or intake funnels and the existing exchange port. Tower modules pay for the new structure through the existing steel-equivalent cost calculation, counting a full station as one kit rather than 60 or 64 kits. Old hand-placed exchange ports remain registered and usable.

## Client and server work

Industrial hangars have opposed banks of telescoping panels on recessed tracks. Panels are at most one metre wide and stack in parallel behind their jambs, including the seven-metre bays. Clients infer opening from the existing synchronized flight plan, opening before even a creative drone reaches the door envelope. The original tower retains roll-up doors. No new per-door block entity, server tick or animation packet exists. Flight lookups are grouped by home position; doors and drone geometry beyond 160 blocks of the camera are omitted, fine moving hardware is limited to 48 blocks, and height matching prevents one flight opening bays on other floors. All upgrades, inventory transfers, ownership, fleet assignment and job completion remain server-authoritative. Existing tower chunk tickets and drone flight scheduling are unchanged.

The live hologram and wall display reuse the terminal snapshot. The complete apron and tower fit inside the table's projection footprint, and the full-height overview leaves the surrounding consoles visible. No new per-frame server request is introduced. World geometry is generated offline and read once per layout.

## Save compatibility and generation

New cores save `layout_version=4`. Cores loaded without that field use layout 1 and frozen `tower.json.gz`; existing layout-2 and layout-3 cores use frozen `tower_industrial_v2.json.gz` and `tower_industrial_v3.json.gz`, with their own ten UI silhouettes. The delivered layout-3 geometry and images were copied byte for byte before this revision. Existing towers retain their saved construction, costs, docking behavior and unfinished tile ordering; shared building material IDs receive the revised artwork. There is no automatic world retrofit. Current industrial geometry uses `tower_industrial.json.gz`; construction, pickups, docking, hologram and upgrade previews use their owning core's version. The explicit industrial build command refuses layouts 1 through 3 and explains how to choose a fresh site. Both foundation blueprint IDs create new layout-4 cores. Later revisions must freeze delivered construction data before advancing the version. Ten building materials use eight static UV phases derived from absolute world position, so adjacent blocks form continuous two-metre sheets without block entities or ticking.

Targeted generation: `python -B tools/tower_realism_art.py --write --preview`, `python -B tools/tower_exchanges.py --write`, and `python -B tools/tower_industrial.py`. These also integrate into the normal material/texture generators. The native model preview reads the actual exported JSON models, texture PNGs and blockstate rotations; it is labelled as an offline preview, not gameplay evidence.

## Review-world slime cleanup

The local startup config `run/config/jugcraft-review-worlds.json` opts in only the exact world folder `Admin Review 6`. On its next normal startup, the mod enables persisted slime cleanup only if that world is singleplayer and flat. Loaded and newly loaded vanilla slimes are discarded without drops; other mobs, gamerules and structures remain unchanged. No save file is edited offline. `/dronetest slimes on` explicitly re-enables slimes and persists that choice, so the startup config does not override it later. The config installer checks the previous config or its absence and the world generator, then backs up the prior config or absence record before writing only the config file.
