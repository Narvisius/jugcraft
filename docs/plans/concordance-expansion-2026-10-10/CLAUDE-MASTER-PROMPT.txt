Use status labels: MAIN, OPEN CONTRIBUTION, OWNER DIRECTION, PROPOSAL and UNVERIFIED. Report discrepancies rather than silently claiming the plan matches changed code. Do not invent existing classes or pretend a conceptual proposed schema already exists.

CRITICAL CONTRACTS
- Server validates intent, knowledge, authority, resources, target and output.
- Existing cast settlement spends once. Delayed/continuous casts need explicit cast identity and cancellation semantics.
- All composition branches/pulses share bounded work and an effect ledger.
- Pylon baseline is 1000 JE to 1 Ley, 64 Ley storage and 64 JE/t intake; 3 Radiance essence to 2 Ley; no reverse conversion.
- Keep seven distinct resources. Bound Will is agreement identity, not fluid.
- Use Fabric transactions and exact item/fluid variants. Courier cargo has one authoritative ledger.
- Preserve restricted equivalence and audit all conversion/salvage/byproduct loops.
- No force-loading for ordinary workers or region scans.
- Lair sessions currently do not resume after restart; return/grave-goods records do.
- Bosses and seasons do not gate core farming, electricity or ordinary magic.
- Existing owner industrial choices stay intact: steel/electricity parallel, automatic gas pressure, no routine machine maintenance, pollution-driven raiders without crop death/smog/biome recoloring.
- Stolas is the first pact, not automatically an enemy. Transformation is voluntary and separate from Vitae.
- Reuse authorized owner assets with provenance; do not redraw them merely to differ.
- Respect generator ownership and preserve stable IDs/saves.
- Do not advertise hypothetical tests as passed.

WORK METHOD
1. Produce a short current-state delta and a chunk contract.
2. Split the selected chunk into three to five reviewable units with a visible player outcome.
3. Build one end-to-end path before adding variants.
4. Reuse actual interfaces and extend only seams needed by working content.
5. Add meaningful regression tests for new correctness risks.
6. Run required and relevant checks; inspect real client output for visual features.
7. Fix discovered issues inside the authorized scope.
8. Update feature documentation, source map, acquisition/progression guidance and provenance.
9. Keep a technical handoff with exact commit, schema changes, commands/results, known gaps and next work.
10. Return the owner checkpoint; wait for input before beginning the next chunk.

CHECKPOINT FORMAT
Use 300–500 words for the owner:
- What the player can now do.
- The meaningful changes.
- What was verified, with exact commit and honest limits.
- Two to four evidence links and a short demo route.
- At most three consequential choices, each with a recommendation.
- The next proposed chunk in two sentences.

Do not stop every few edits to ask ordinary implementation questions. Do not deliver only a plan when the selected task authorizes implementation. Do not run through the whole roadmap without the requested check-ins.

IF USING MULTIPLE AGENTS
Use them only when authorized by the owner or applicable environment instructions. Give each a bounded task and agreed interface. One integrator owns shared registries, generators and cross-cutting schemas. Avoid concurrent edits to the same files. Record actual model attribution; preserve OpenAI Codex attribution for this planning pack and original authors of existing features.

COMPLETION
A chunk is complete when its promised player experience works, relevant validation is recorded, documentation is accurate and the owner can review a concrete result. A placeholder UI, rendered model, creative-only item or passing compiler does not by itself satisfy that standard.

No public server needs to be running for development. Use isolated local/staging tests where available. Mark two-account human tests unverified if unavailable; do not pretend a one-client automated test substitutes for them. Publication/deployment follows the current owner authorization and repository release rules.
